## 1. 问题现象

用户在腾讯广告（ad.qq.com）充值流程走完后点充值页/回调页的"**返回**"按钮，**整个浏览器（所有标签页）偶发性整体退出**，表现为闪退。v1.3.82/83 已有守卫仍复现，且退出日志把它记成了"用户点X正常退出"。

## 2. 运行时/框架

- Electron 44.0.0（Chromium 152），Windows 10/11
- 标签页 = BrowserView（非 webview 标签），主窗口 `frame: true, titleBarStyle: 'default'` **原生标题栏**
- 原生标题栏意味着：用户点 X = 系统 WM_CLOSE 直达 `mainWindow 'close'` 事件，与程序化 `mainWindow.close()` 在事件层面**完全无法区分**

## 3. 根因分析（日志实锤，别再猜）

退出日志 `exit-latest.log` 关键片段（2026-09-06 17:39:42，同一秒内连续发生）：

```
[NAV] did-start-navigation url=https://shop-promotion.qq.com/public/protocol/midasCallback.html?pf=midas_group_pay-1000-html5-1000&outTradeNo=qyt-2-... isMainFrame=true
[NAV] will-frame-navigate url=... isMainFrame=false
[NAV] will-navigate url=...
[QUIT-DIAG] mainWindow close(无页面关闭信号,视为用户点X,正常退出)   ← 误判全退
[COOKIE] 备份会话Cookie失败 all.filter is not a function           ← 顺带发现的第二个bug
```

防线为什么全部失守（三层）：

| 层 | 机制 | 失守原因 |
|---|---|---|
| ① window.close 注入桩 | `did-start-navigation` 时 `executeJavaScript` 往主帧注入 `window.close = function(){ dispatchEvent(...) }`，经 preload 的 DOM 自定义事件转发 IPC 上报 | **异步竞态**：桩注入落地前页面脚本可能已调用 `window.close()`（所以"偶尔"）；**子 frame 调用完全无覆盖**（executeJavaScript 只进主帧） |
| ② webContents 'close' 事件监听 | `event.preventDefault()` | **Electron 44 已不触发**（文档移除，实测无效） |
| ③ 主窗口 close 守卫（v1.3.82） | 3 秒内有页面关闭信号→拦截；无信号→当用户点X放行 | 页面 close 请求绕过①直达主窗口，无信号 → **误判为用户点X** |

关键认知：**Chromium 会把页面发起的 `window.close()` 请求冒泡给宿主 BrowserWindow**，在 Electron BrowserView 架构下就是关闭整个 app。这是腾讯系页面（充值回调 midasCallback.html 等）的固有行为。

## 4. 核心修复/封装（v1.3.84，`src/main.js`）

### 4.1 光标归因兜底（主窗口 close 守卫增强）

**原理**：原生标题栏的 X 按钮物理位置固定在**窗口右上角**。无页面关闭信号时，用鼠标光标位置做第二重归因：

- 光标**不在**右上角区域（约 100×80 DIP，以窗口 getBounds 计算）→ 必然不是点 X → 判定为页面冒泡关闭 → `preventDefault()` 拦截，浏览器保持运行
- 光标**在**右上角区域 → 判定为用户点 X → 正常退出

代码位置：`mainWindow.on('close')`（约 821-850 行），`screen` 已加入顶层 require：

```js
if (!globalState.isQuitting) {
  const sinceSignal = Date.now() - (globalState.lastPageCloseSignal || 0);
  if (sinceSignal < 3000) {
    // 第一重：3秒内有关闭信号（桩上报/destroyed）→ 拦截
    event.preventDefault(); ... return;
  }
  // 第二重（v1.3.84）：无信号但光标不在X区域 → 页面绕桩关闭 → 拦截
  let cursorAtX = false;
  try {
    const cp = screen.getCursorScreenPoint();
    const wb = mainWindow.getBounds();
    cursorAtX = (cp.x >= wb.x + wb.width - 100) && (cp.y <= wb.y + 80);
  } catch (e) { cursorAtX = false; }
  if (!cursorAtX) {
    event.preventDefault();
    addLog('CLOSE-FIX', '页面关闭请求绕过桩被拦截(光标不在X按钮区域,浏览器保持运行)', ...);
    return;
  }
  // 光标在X区域 → 用户点X → 正常退出
  globalState.isQuitting = true;
}
```

日志标识：`CLOSE-FIX | 页面关闭请求绕过桩被拦截(光标不在X按钮区域,浏览器保持运行)`

### 4.2 Cookie 备份报错修复（backupSessionCookies，约 6273 行）

Electron 44 下 `session.cookies.get({})` 可能返回非数组（Promise 等），`.filter` 直接炸：

```js
let all = ses.cookies.get({});
if (!Array.isArray(all) && all && typeof all.then === 'function') {
  try { all = await all; } catch (e) { all = []; }
}
if (!Array.isArray(all)) all = [];
```

## 5. 入参/出参与状态字段

| 字段/函数 | 说明 |
|---|---|
| `globalState.lastPageCloseSignal` | 最近一次页面关闭信号时间戳（桩上报 / webContents destroyed 写入）；0=无 |
| `globalState.isQuitting` | 主动退出标记（托盘退出/app.quit 置 true，close 守卫直接放行） |
| `screen.getCursorScreenPoint()` | 全局光标屏幕坐标（物理像素） |
| `mainWindow.getBounds()` | 窗口 {x,y,width,height}，DIP 单位；X 区域判定用右上角 100×80 DIP |

## 6. 异常与边界（重要，复现排查先看这里）

1. **Alt+F4 误拦**：用键盘关浏览器且光标不在右上角时，会被兜底拦截一次（浏览器不退）。再点一次 X（光标在 X 上，直接放行）或用托盘「退出」。**这是已知取舍**：鼠标点 X 是用户主习惯，防闪退优先。
2. **光标恰好停在右上角时页面 close**：仍会放行全退（和修复前一样）。概率极低，可接受。
3. 若日志出现 `CLOSE-FIX` 拦截记录但用户坚持"我真的是点 X 退的"，检查：是否双显示器（光标坐标跨屏）、缩放比例异常（>200% 时 100×80 DIP 可能不够，可把 100/80 调大到 140/110）。
4. 验证方法：进腾讯广告充值流程（或任何会 window.close 的回调页）点"返回"→ 浏览器应保持运行，日志出现 CLOSE-FIX 拦截记录。

- **退出日志位置**：`C:\Users\Administrator\AppData\Roaming\feimaotui-browser\browser-data\logs\exit-latest.log`（每次启动会归档为 exit-<时间戳>.log）；排查闪退先看这里面最后 20 行有没有 QUIT-DIAG/CLOSE-FIX。
- **守卫分层记忆口诀**：信号拦截（3秒）→ 光标归因（无信号兜底）→ 用户X放行。改守卫逻辑时三层顺序不能乱。
- **教训**：凡是"依赖页面脚本配合"的防御（注入桩）都有竞态，**守卫端必须有不依赖页面配合的兜底**。
